# Архитектурное предложение — Ausstellerportal MOTO-ZÜRICH 2027

**Статус:** предложение, не реализовано. Версия от 2026-08-11.
**Что решает:** как превратить прототип (один `index.html` с демо-данными) в рабочий кабинет экспонента к сезону 2027.

---

## 1. Контекст

Выставка — **19–21 февраля 2027**, StageOne + Halle 550, Zürich-Oerlikon. Монтаж 17–18.02, демонтаж 21–22.02.

Продажа стендов и сбор данных экспонентов идут **осенью 2026** — то есть портал нужен раньше, чем сама выставка, и первая же реальная нагрузка на него придётся на период Anmeldung.

Сейчас в проде — прототип: один самодостаточный `index.html` (~87 КБ, 1355 строк), 11 разделов, всё состояние в памяти страницы, бейдж «Prototyp», данные вымышленные, входа нет. Прототип — не мусор, а **готовая функциональная спецификация**: в нём промоделированы план залов со статусами площадок, часовые слоты доставки с квотами, заказ техники, балльная система совместного маркетинга, пропуска, переписка с Messeleitung. Разработка идёт «по прототипу», а не с чистого листа.

### Принятые решения

| Решение | Выбор |
|---|---|
| Бэкенд | Отдельное Next.js-приложение в репо портала (не в общем `slswiss-tickets`) |
| Вход | Supabase Auth, email + одноразовый код |
| База | Отдельный проект Supabase под MOTO-ZÜRICH |
| Админка Messeleitung | В первой очереди нет — письма + правка в дашборде Supabase |
| Очерёдность | Этап 1 — вход · Этап 2 — заявка на стенд и профиль · Этап 3 — остальное |
| Среда разработки | Локально, с установленным Node |

### Что берём из `slswiss-tickets` без изменений

- **Ленивая инициализация клиентов** (`lib/supabase.js`, паттерн Proxy). Без неё `next build` на Vercel падает — переменных окружения во время сборки нет. То же для Resend.
- **`runtime = 'nodejs'`** в каждом роуте.
- **Порядок гардов в роуте**: нет env → 503, нет прав → 401/403, кривой ввод → 400, и только потом обращение к базе.
- **`escapeHtml`** и правило «экранирует вызывающая функция, а не шаблон».
- **Письмо не валит операцию**: ошибка Resend логируется, но не откатывает сохранённую заявку.
- **Трёхслойные тесты** под одним раннером Playwright.

## 3. Аутентификация

Здесь главное архитектурное противоречие, и его надо снять явно.

Модель платформы — **RLS deny-all**: строки закрыты для всех, доступ только через `service_role` с сервера. Supabase Auth же обычно предполагает обратное: браузер с anon-ключом ходит в базу напрямую, а доступ разграничивают RLS-политики по `auth.uid()`.

**Предлагаю первый вариант: Supabase Auth только для установления личности, все данные — через свои API-роуты.**

```
Браузер ──anon-ключ──▶ Supabase Auth   (только вход: отправка кода, проверка кода, выход)
   │
   │ cookie сессии
   ▼
Наш API-роут ──▶ getUser() проверяет сессию ──▶ определяет компанию
                                              ──▶ service_role читает/пишет данные этой компании
```

RLS на всех таблицах включён, политик — ноль. Браузер, даже имея anon-ключ, не может прочитать из базы ничего.

**Почему так, а не через RLS-политики.** Правила доступа живут в одном месте — в коде роутов, на JavaScript, который можно прочитать, отладить и покрыть Playwright-тестами. Забытая политика в SQL — это тихая утечка данных одной компании другой; забытая проверка в роуте — это упавший тест. Для проекта, который ведёт не профессиональный разработчик и который к февралю 2027 будет содержать реальные данные десятков компаний, предсказуемость важнее элегантности.

**Чем платим.** Каждый экран требует своего роута — «просто читать таблицу из браузера» не выйдет. Не будет realtime-подписок. Кода больше. Считаю цену оправданной; если на этапе 3 упрёмся в объём, отдельные read-only разделы можно будет перевести на RLS-политики точечно, но начинать с этого не стоит.

### Поток входа

1. Экспонент вводит рабочий email.
2. `POST /api/auth/request-code` сверяет адрес со **списком допущенных** (`mz_allowlist`). Адреса в список вносит Messeleitung.
3. Нет в списке → честный ответ: «Эта почта не открыта для портала» + контакт Messeleitung + ссылка на публичную заявку на участие. Никаких кодов не шлём.
4. Есть в списке → Supabase отправляет шестизначный код на почту.
5. `POST /api/auth/verify` проверяет код, ставит cookie сессии, при первом входе связывает `auth.users.id` с компанией через `mz_company_members`.
6. Дальше каждый запрос: сессия → пользователь → его компания → данные только этой компании.

**Важная деталь безопасности.** У Supabase Auth по умолчанию включено автосоздание пользователя при запросе кода. Anon-ключ виден в браузере, поэтому кто угодно смог бы дёрнуть отправку кода на любой адрес — это готовый спам-канал с нашего домена. Поэтому: `shouldCreateUser: false`, а учётные записи создаём мы сами админским API в момент внесения адреса в allowlist.

**Несколько сотрудников от компании** поддерживаются с самого начала: связь «пользователь ↔ компания» вынесена в отдельную таблицу. Уход сотрудника = удаление строки из allowlist и из membership, доступ пропадает при следующем входе.

## 4. Модель данных

Префикс `mz_` — на случай, если базу когда-нибудь сольют с платформенной.

### Этап 1–2 (подробно)

```sql
-- Компании-экспоненты
create table public.mz_companies (
  id            uuid primary key default gen_random_uuid(),
  name          text not null,
  uid_nummer    text,                    -- CHE-…
  strasse       text,
  ort           text,
  kontakt_name  text,
  kontakt_tel   text,
  rechnungs_email text,
  -- Verzeichniseintrag (сайт, приложение, Event-Guide)
  kategorie     text,                    -- Motorräder, Zubehör, Bekleidung, …
  website       text,
  brands        text[],
  beschreibung  text,                    -- до 300 знаков
  public_email  text,
  instagram     text,
  logo_path     text,                    -- ключ в Storage
  status        text not null default 'interessent'
                check (status in ('interessent','angemeldet','bestaetigt','abgesagt')),
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now()
);

-- Кто допущен ко входу. Ведёт Messeleitung.
create table public.mz_allowlist (
  email       text primary key,          -- в нижнем регистре
  company_id  uuid not null references public.mz_companies(id) on delete cascade,
  rolle       text not null default 'mitarbeiter'
              check (rolle in ('inhaber','mitarbeiter')),
  eingeladen_am timestamptz not null default now(),
  aktiv       boolean not null default true
);

-- Связь учётной записи с компанией. Пишется при первом входе.
create table public.mz_company_members (
  user_id     uuid primary key references auth.users(id) on delete cascade,
  company_id  uuid not null references public.mz_companies(id) on delete cascade,
  rolle       text not null default 'mitarbeiter',
  erster_login timestamptz not null default now()
);
create index on public.mz_company_members (company_id);

-- Каталог площадок. Геометрия и статусы.
create table public.mz_stands (
  id          text primary key,          -- 'D09', 'H14'
  halle       text not null,             -- 'Halle D' | 'Halle 550' | 'StageOne'
  lage        text,                      -- 'Mittelblock, Nordgang'
  breite_m    numeric(5,2) not null,
  tiefe_m     numeric(5,2) not null,
  flaeche_m2  numeric(6,2) generated always as (breite_m * tiefe_m) stored,
  pos_x       numeric(6,2) not null,     -- координаты для SVG-плана
  pos_y       numeric(6,2) not null,
  status      text not null default 'frei'
              check (status in ('frei','reserviert','vergeben','gesperrt')),
  company_id  uuid references public.mz_companies(id) on delete set null,
  created_at  timestamptz not null default now()
);
create index on public.mz_stands (status);

-- Заявки на площадку
create table public.mz_stand_requests (
  id           uuid primary key default gen_random_uuid(),
  company_id   uuid not null references public.mz_companies(id) on delete cascade,
  stand_id     text references public.mz_stands(id) on delete set null,
  user_id      uuid references auth.users(id) on delete set null,
  wunsch_text  text,
  status       text not null default 'neu'
               check (status in ('neu','in_pruefung','offeriert','angenommen','abgelehnt')),
  bearbeitet_am timestamptz,
  notiz_intern text,
  created_at   timestamptz not null default now()
);
create index on public.mz_stand_requests (company_id);
create index on public.mz_stand_requests (status);

-- Журнал действий: кто что менял. Нужен, когда за компанию работают двое.
create table public.mz_audit (
  id         bigserial primary key,
  company_id uuid references public.mz_companies(id) on delete cascade,
  user_id    uuid references auth.users(id) on delete set null,
  aktion     text not null,
  details    jsonb,
  created_at timestamptz not null default now()
);

-- RLS: включён везде, политик нет — доступ только через service_role
alter table public.mz_companies       enable row level security;
alter table public.mz_allowlist       enable row level security;
alter table public.mz_company_members enable row level security;
alter table public.mz_stands          enable row level security;
alter table public.mz_stand_requests  enable row level security;
alter table public.mz_audit           enable row level security;

revoke truncate on public.mz_companies, public.mz_allowlist, public.mz_company_members,

```

**Почему статусы стенда в базе, а не в коде.** В прототипе `vergeben`/`reserviert` — массивы в JS, и «Stand anfragen» просто дописывает id в массив. В реальности статус площадки — то, что Messeleitung правит руками между звонками, и именно он должен мгновенно отражаться в плане у всех.

### Этап 3 (список таблиц)

`mz_slots` и `mz_slot_bookings` (Anlieferung/Abtransport с квотами — единственное место, где возможна гонка за последний свободный слот, нужна транзакция), `mz_parking_orders`, `mz_service_orders` + `mz_service_catalog` (техника), `mz_marketing_orders` + `mz_marketing_catalog`, `mz_koop_measures` и `mz_koop_proofs` (баллы и нахвайсы, включая недостающий в прототипе переход в статус «bestätigt»), `mz_activities`, `mz_badges`, `mz_documents`, `mz_invoices`, `mz_messages`.

### Файлы

Один приватный бакет `ausstellerportal`, политик доступа ноль — как и у таблиц, читает и пишет только сервер ключом `service_role`. Путь: `<company_id>/<слот>/<uuid>-<имя>`.

Идентификатор компании стоит первым сегментом намеренно: тогда чужой файл нельзя отдать по ошибке в коде — несовпадение префикса видно сразу и при чтении кода, и в дашборде.

Наружу файл попадает **только подписанной ссылкой** на десять минут, которую выдаёт роут после проверки прав. Публичный URL логотипа был бы перечислимым списком экспонентов: зная схему адресов, посторонний узнаёт состав участников до анонса.

Проверка типа и размера — на сервере. Атрибут `accept` в разметке подсказывает человеку, но не защищает: запрос можно отправить мимо формы.

**Слоты загрузки в прототипе — восемь.** Хранилище спроектировано сразу под все, чтобы не переделывать под каждый раздел:

| Раздел | Слот | Что грузят | Особенность |
|---|---|---|---|
| Firmenprofil | `pLogo` | логотип | ✅ сделано |
| Marketing → News | `nwFile` | изображение к новости | после модерации публикуется |
| Marketing → Event-Guide | `agFile` | печатные макеты, много | тяжёлые PDF, десятки МБ |
| Marketing → Design | `spFiles` | исходники для дизайнера | оригиналы логотипов и фото |
| Marketing → Änderung | `wcFile` | приложение к заявке | мелочь |
| Gemeinsame Aktivitäten | `kFile` | нахвайсы: скриншоты, фото | чужие лица и ники в кадре |
| Ausweise & Tickets | `mlFile` | список персонала Excel/CSV | **персональные данные сотрудников** |
| Aktivitäten am Stand | `aBild` | изображение к активности | идёт в программу |

Плюс обратное направление: в разделе Dokumente & Rechnungen файлы идут *от нас* — AGB, Technisches Merkblatt, план монтажа, счета. Кладёт Messeleitung, экспонент только скачивает.

**SVG для логотипа не принимается.** Внутри SVG может лежать скрипт, а логотип попадает на сайт и в приложение. Растрового формата для каталога достаточно, для печати макет приходит отдельным каналом.

**Ограничение тарифа, о котором надо помнить:** хранилище Supabase на бесплатном плане — 1 ГБ. Печатные макеты от сорока экспонентов съедят его за неделю. Поэтому поля «или дайте ссылку», которые стоят в прототипе рядом с каждой загрузкой, — основной путь для тяжёлого, а не запасной. У себя храним то, что действительно нужно держать: логотипы, изображения каталога, нахвайсы, списки персонала.

## 5. Что делать с прототипом

Он в проде, и на него могли уже дать ссылки. Ломать его посреди разработки нельзя.

- Разработка идёт в ветке, `main` до конца этапа 1 не трогаем — прототип продолжает жить как есть.
- При первом мерже: `/` становится экраном входа, а прототип переезжает в `public/prototyp.html` и остаётся доступен по адресу `/prototyp` как справочный макет.
- Разделы, которые ещё не переведены на бэкенд, показываются в новом кабинете с той же честной пометкой «Prototyp» — то есть человек видит, что раздел пока демонстрационный, а не думает, что его заказ ушёл.
- Красные даты `XX.XX.2027` остаются красными, пока Messeleitung не назовёт реальные сроки. Это не техдолг, это корректная индикация незаполненных бизнес-данных.

## 6. Этапы

### Этап 0 — фундамент
Каркас Next.js в репо, `package.json`, `playwright.config.js`, CI, первый деплой ветки на preview, отдельный проект Supabase, `supabase/schema.sql` применён. **Готово, когда:** preview-деплой открывается, CI зелёный, база создана.

### Этап 1 — вход
Экран входа, три роута аутентификации, `lib/auth.js`, гард на `/portal`, allowlist, письмо с кодом, страница Datenschutz. **Готово, когда:** реальный человек из списка входит по коду со своей почты, чужой адрес получает отказ без письма, выход работает, тесты прав зелёные.

Критический путь этапа — **не код, а почта**: пока домен-отправитель не верифицирован в Resend, код на почту не уйдёт и проверить будет нечего. Начинать с DNS, а не с вёрстки.

### Этап 2 — заявка на стенд и профиль
План залов из базы, `Stand anfragen` пишет заявку и уведомляет Messeleitung письмом, Firmenprofil сохраняется и отдаётся при следующем входе, загрузка логотипа. **Готово, когда:** заявка видна в Supabase и в почте, профиль переживает перезаход, экспонент A не может прочитать профиль экспонента B.

### Этап 3 — остальные разделы
По убыванию пользы: Anreise (слоты) → Technik (заказ) → Ausweise (персонал) → Nachrichten → Marketing и Gemeinsame Aktivitäten → Dokumente. Счета — отдельно, см. ниже.

## 7. Тесты

Четыре слоя, как в `slswiss-tickets`, плюс пятый под аутентификацию.

| Слой | Что проверяет | Внешние сервисы |
|---|---|---|
| `tests/unit` | чистые функции `lib/` — геометрия плана, валидация профиля, расчёт баллов | не нужны |
| `tests/integration` | настоящие роуты через `request`-фикстуру: гарды до базы — нет сессии → 401, чужая компания → 403, кривой ввод → 400 | не нужны |
| `tests/e2e` | страницы через `next dev`, наши API замоканы `page.route` | не нужны |
| `tests/pgtap` | инвариант «RLS включён, политик ноль» | нужна база |
| `tests/live` | реальный вход против тестового проекта Supabase | нужна тестовая база |

**Права доступа — главный класс багов кабинета,** и проверять их выборочно бессмысленно. Предлагаю тест, который перебирает **все** company-scoped роуты списком и для каждого утверждает три вещи: без сессии → 401, с сессией чужой компании → 403, со своей → 200. Новый роут, забытый в списке, роняет тест — то есть список нельзя не пополнить.

**Как тестировать вход без реальных писем.** Supabase умеет выдавать код админским API, не отправляя письмо (`auth.admin.generateLink`). На этом строится слой `tests/live`: тест создаёт временного пользователя, получает код напрямую, проходит вход целиком. Это единственный способ проверить настоящий вход автоматически. Гонять его в каждом PR не нужно — он требует ключей от тестовой базы; место ему в ручном и ночном прогоне.

**Честно о границах.** Тестами не покрываются: доставляемость писем (проверяется по логам Resend), корректность DNS, поведение под реальной нагрузкой февраля. Для них — ручной чек-лист.

CI повторяет платформенный: node 20, `npm ci`, `npm run build` (ловит синтаксические ошибки всех роутов без env), установка chromium, `npx playwright test`. Заглушки env — в `playwright.config.js`; работают потому, что клиенты ленивые.

**Почта — критический путь.** Проверено 2026-08-11: в Resend было три домена (`slswiss.ch`, `frankenplatz.ch`, `atlasintegra.ch`, все verified, Ireland), `motozuerich.ch` среди них не было. Пока он не верифицирован, письма экспонентам уходят от «SoiLüDi» — чужой бренд в письме со ссылкой на вход выглядит как фишинг.

Сделано: домен `motozuerich.ch` заведён в Resend (регион eu-west-1, отправка включена, приём и трекинг выключены), три DNS-записи переданы Иву для Hostpoint — TXT `resend._domainkey`, MX `send` → `feedback-smtp.eu-west-1.amazonses.com` prio 10, TXT `send` → `v=spf1 include:amazonses.com ~all`. **Корневые MX и SPF не трогаем.** Осталось: дождаться внесения записей и запустить проверку. На время разработки письма можно слать с уже верифицированного домена платформы.

**Адреса писем — решено 2026-08-11.** Отправитель `noreply@motozuerich.ch`, `Reply-To` — **`yves@motozuerich.ch`**, живой ящик. Приём на домене в Resend выключен, поэтому ответы уходят не нам в обработку, а человеку напрямую — так и задумано.

**Перехват получателя на тестовых окружениях.** Переменная `PORTAL_MAIL_OVERRIDE` — если задана, все письма идут на неё вместо настоящего получателя, а настоящий адрес подставляется в тему: `[TEST → firma@example.ch] …`. На Preview и Development ставим `assistant@creox.ch`, в Production переменной быть не должно.

Перехват включается только явной переменной, а не автоматически «когда не прод». Автоматика здесь опаснее: одна ошибка в определении окружения — и боевая почта молча уходит в тестовый ящик, чего никто не заметит, потому что жалоб не будет. Реализовано в `lib/mail.js`, поведение закреплено юнит-тестами.

**Встроенная отправка Supabase против Resend.** У встроенного SMTP жёсткие лимиты (единицы писем в час) и он прямо не предназначен для боевого использования — на пике Anmeldung вход просто перестанет работать. Предлагаю сразу прописать Resend как кастомный SMTP в настройках Supabase Auth.

**Адрес портала.** Предлагаю `ausstellerportal.motozuerich.ch` — CNAME на Vercel, отдельный проект остаётся отдельным. Обоснование: экспонент получает письмо со ссылкой на знакомый домен выставки, а не на `*.vercel.app`; cookie сессии живёт на своём поддомене и не пересекается с основным сайтом. Делается своими силами в Hostpoint.

**Формы вокруг портала.** Публичная заявка на участие от компании, которой ещё нет в списке, — это данные экспонента, а не маркетинговая аудитория, поэтому предлагаю принимать её своим роутом в свою таблицу, а не через платформенный `/api/forms`. Отклонение от правила «один эндпоинт на все сайты» осознанное: там единая база аудитории, здесь — операционные данные выставки в отдельной базе.

**Аналитика.** Портал — кабинет, а не витрина. GA4 и Meta Pixel не нужны, куки-баннер тоже. Достаточно Vercel Web Analytics: он не ставит куки.

**Счета.** Интеграции с бухгалтерией не существует, и в первой очереди её не будет. Предлагаю дешёвую замену на этапе 3: Messeleitung кладёт PDF счёта в Storage, экспонент видит его в разделе Rechnungen. Это закрывает реальную потребность («где мой счёт») без интеграции. До тех пор в разделе остаётся честный пустой текст, который там уже есть.

**Приватность репозитория.** Сейчас репо публичный. Как только в нём появятся роуты и схема базы, его стоит закрыть — но на плане Vercel Hobby приватные репозитории организации не деплоятся. То есть приватность привязана к переходу на Pro, который и так нужен к февралю 2027.

## 11. Реальный процесс продажи площади

Описан Ксенией 2026-08-11. Раньше в этом документе была моя гипотеза «доступ выдаётся после оплаты» — она неверна: **доступ выдаётся после согласования заявки, а счёт приходит уже внутрь портала.**

```
план залов (открыт всем, входа не требует)
   ↓ человек видит свободное место, цену не видит
вводит свой email
   ↓ цена показывается сразу на экране
заполняет заявку «хочу это место»
   ↓ заявка уходит нам
согласование — по телефону, почте, как получится
   ↓
отдельным письмом отправляем приглашение в портал
   ↓
кабинет: профиль, счёт, вся остальная информация
```

**Главное следствие: у продукта две половины, а не одна.**

- **Витрина** — публичная. План залов со статусами площадок, показ цены в обмен на email, форма заявки, уведомление нам. Аутентификации не требует вовсе.
- **Кабинет** — закрытый. Всё, что после приглашения.

«Stand anfragen» из прототипа принадлежит витрине, а не кабинету: к первому входу площадка уже согласована. Внутри кабинета план залов нужен в основном показывающий — «вот ваш стенд D09, 10 × 8 м, Halle D» — а заявка остаётся для другого случая: расширить площадь или поменять место.

**Очерёдность — решение 2026-08-11: сначала кабинет, витрина позже.** Отмечу для истории, что витрина не заблокирована ничем из нашей текущей очереди: ей не нужны ни Supabase Auth, ни верифицированный DKIM. Единственное, что её держит, — отсутствие модели цен. Если осенняя продажа площадей начнёт гореть, витрину можно вставить в работу в любой момент, не ломая начатое.

**Выдача доступа — решение 2026-08-11: письмо-приглашение ведёт на страницу входа, где человек вводит свою почту и получает код.** Ссылка сама по себе ничего не открывает.

Причина: ссылка-автовход — это пароль, лежащий в почтовом ящике. Её пересылают коллеге «посмотри», она остаётся в переписке на годы, и любой, кто получил доступ к ящику или к цепочке писем, входит в кабинет компании. Код живёт минуты и привязан к попытке входа. Заодно механизм входа остаётся один и тот же и для первого раза, и для всех последующих — не нужно отдельно строить и объяснять два пути.

**Про сбор email в обмен на цену.** Это персональные данные, собранные до всякого договора, поэтому форма обязана иметь галочку согласия — по тем же правилам, что все формы платформы. Отдельно стоит понимать размен: гейт увеличивает число контактов, но часть людей уйдёт, не назвавшись, а часть введёт мусорный адрес. Это решение бизнеса, не техники.

**Следствие из «списка нет».** Портал стартует пустым, значит первые компании заводятся руками. В первой очереди админки нет, то есть Ив и Ксения будут добавлять строки в таблицу прямо в дашборде Supabase. Это осознанный размен: экономим на админке, платим риском ручной правки боевой таблицы двумя людьми без опыта работы с SQL. Пока компаний единицы — приемлемо; как только их станет десятки, простая админка окупится, и это первый кандидат в этап 3.

**В чём я не уверена.**
- Выбор «свои роуты вместо RLS-политик» — это ставка на предсказуемость против скорости. Если разделов этапа 3 окажется много, объём роутов станет заметным, и часть read-only экранов, возможно, стоит будет перевести на прямое чтение с политиками. Пересмотреть это разумно после этапа 2, на реальных цифрах, а не сейчас.
- Оценки трудоёмкости этапов я сознательно не даю: в проекте слишком много неизвестных бизнес-данных, и любые сроки сейчас были бы выдуманными.
